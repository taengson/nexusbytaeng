### ✅ Hermes ACP 스펙 (소스 코드 분석 완료)

**핸드셰이크 시퀀스:**
```
클라이언트 → 서버: initialize(protocol_version: int, client_info)
  method: "initialize"
서버 → 클라이언트: InitializeResponse(protocol_version, agent_info, agent_capabilities)
클라이언트 → 서버: new_session(cwd: str)
  method: "session/new"
서버 → 클라이언트: NewSessionResponse(session_id: str, models, modes)
```

**JSON-RPC Method 이름 (acp.meta 기준):**
- Agent methods (서버 수신): `initialize`, `session/new`, `session/prompt`, `session/cancel`, `session/close`, `session/load`, `session/resume`, `session/fork`, `session/list`
- Client methods (서버 발송): `session/update`, `session/request_permission`, `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/kill`, `terminal/wait_for_exit`

**프롬프트 흐름:**
```
클라이언트 → 서버: prompt(session_id, prompt: ContentBlock[])
  ContentBlock 타입: TextContentBlock, ImageContentBlock, ResourceContentBlock 등
  간단한 텍스트: [{text: "사용자 입력"}]

서버 → 클라이언트 (실시간 스트리밍, session_update notification):
  - update_agent_message_text(text) → AI 응답 텍스트 스트리밍
  - update_agent_thought_text(text) → 생각/추론 과정
  - ToolCallStart(tool_call_id, name, args) → 도구 호출 시작
  - ToolCallComplete(tool_call_id, name, result) → 도구 호출 완료
  - AgentPlanUpdate(entries) → todo/plan 업데이트

서버 → 클라이언트: PromptResponse(stop_reason: "end_turn" | "refusal")
```

**핵심 특징:**
- `protocol_version`은 **int형** — hermes의 `acp.PROTOCOL_VERSION` = **`1`** (반드시 `1`로 보낼 것)
- stdout은 JSON-RPC 전용, stderr는 로그 출력용 (분리됨)
- `session_update`는 **server-to-client notification** (id 필드 없음)
- 프롬프트 완료는 `PromptResponse`의 `stop_reason`으로 확인
- hermes는 `acp.run_agent()`로 서버 실행 — `agent-client-protocol` Python 패키지 의존

### ⚠️ 핵심 주의 (개발자必读)
1. **protocolVersion은 숫자** — string으로 보내면 `-32602 Invalid params` 에러 발생
2. **에이전트별 에러 형식 차이** — `data._errors` vs `data.errors[]` 유연 파싱 필요
3. **hermes acp는 에이전트 서버** — hermes가 내부 tool 실행. UI는 `session_update` 수신만 하면 됨
4. **JSON-RPC notification은 id 없음** — `session_update` 응답 대기 금지 (unidirectional)
5. **프로세스 생명주기** — 에이전트 프로세스는 시작 후 계속 살아남. `kill()` 호출로 종료 필요
6. **ContentBlock 입력** — `prompt` 호출 시 `[{text: "메시지"}]` 배열 형식 사용

## 🔍 [리뷰어] UI 동작 불일치 분석 및 의견 요청 (2026-07-23)

**현상:** 
`test_acp/test_acp.py`를 통한 직접 통신 테스트에서는 핸드셰이크부터 스트리밍 응답까지 모든 기능이 정상 동작하지만, 동일한 로직을 적용한 Nexus UI(앱) 내에서는 응답이 출력되지 않거나 동작하지 않는 현상이 발생함.

**분석 및 가설:**
구현 코드는 테스트 코드와 1:1로 일치함(중첩 구조 파싱, 필수 파라미터 등). 따라서 통신 로직 자체보다는 **UI 레이어의 특성**에 의한 문제로 추정됨.

1. **UI 렌더링 지연/누락**: `test_acp.py`는 즉시 `print` 하지만, Textual UI는 `update_last_ai_message` 호출 후 리렌더링 주기까지 시차가 있으며, 매우 빠른 스트리밍 시 업데이트가 씹히거나 지연될 가능성.
2. **`sessionId` 설정 레이스 컨디션**: `on_mount`에서 `create_session` 응답 수신 후 `set_session_id`를 호출하는데, 그 전에 서버가 `session/update` Notification을 먼저 보내면 `session_id`가 없는 상태에서 메시지가 무시될 가능성.
3. **에이전트별 스펙 미세 차이**: Hermes 외의 에이전트 사용 시 `params["update"]` 중첩 구조를 쓰지 않는 경우, 현재의 중첩 파싱 로직이 모든 메시지를 `None`으로 처리하여 무시함.

**리뷰어 요청 사항:**
- 위 가설 중 Textual UI 환경에서 특히 주의해야 할 점이나, `session/update` 수신 시 UI 스레드 안전성을 보장하며 즉각적으로 텍스트를 반영할 수 있는 더 최적화된 패턴이 있는지 검토 요청.
- 다양한 에이전트 서버 간의 `session/update` 구조 차이를 유연하게 처리할 수 있는 권장 파싱 전략 제안 요청.

### 문제 2: `send_request()`가 응답을 기다리지 않음 — 핸드셰이크 완료 보장 없음

**현재 코드** (`acp.py:124-142`):
```python
async def send_request(self, method, params):
    # ... stdin에 메시지 전송
    await self.process.stdin.drain()
    # Note: This simplified client doesn't wait for the response match
    return request  # ← 응답이 아닌 요청 객체 반환
```

**`on_mount()`의 흐름** (`session_workspace.py:83-95`):
```python
await self.acp_client.initialize()    # ← 요청만 보내고 즉시 반환
resp = await self.acp_client.create_session(cwd=".")  # ←同上
# session_id가 아직 설정되지 않은 상태에서 계속 진행
```

→ `initialize()`와 `create_session()`의 응답이 도착하기 전에 코드가 계속 진행됨. `session_id` 설정은 `_handle_acp_message`에서 뒤늦게 처리되므로, 사용자가 메시지를 보내면 `session/prompt`가 `RuntimeError("Session not initialized")`로 실패.

**수정 방향 — `asyncio.Future` 기반 응답 매칭:**
```python
# ACPClient에 추가
self._pending: Dict[int, asyncio.Future] = {}

async def send_request(self, method, params):
    self.request_id += 1
    # ... 요청 전송
    # 응답을 기다리는 Future 등록
    future = asyncio.get_event_loop().create_future()
    self._pending[self.request_id] = future
    return await asyncio.wait_for(future, timeout=10)

async def _handle_response(self, data):
    req_id = data.get("id")
    if req_id in self._pending:
        future = self._pending.pop(req_id)
        if not future.done():
            future.set_result(data)
```

이렇게 하면 `initialize()`와 `create_session()`이 실제 응답을 받을 때까지 블로킹됨.

### 문제 3: 연결 대기 UI — Toad 패턴 참고

Toad의 ACP 연결 흐름:
1. 세션 시작 → 입력창 **비활성화** (`can_focus = False`)
2. 시스템 메시지: "🔄 에이전트 서버 연결 중..." 출력
3. 핸드셰이크 진행 (initialize → session/new)
4. 핸드셰이크 완료 → 입력창 **활성화** + "✅ 연결됨" 메시지
5. 실패 시 → 입력창 활성화 + "❌ 연결 실패: 원인" 메시지

**현재 구현에서 누락된 부분:**
- 입력창 비활성화/활성화 로직 없음
- 핸드셰이크 진행 상태 표시 없음 (시스템 메시지 "통신 중입니다"만 있으며, 완료/실패 구분 없음)
- 연결 중 사용자 입력 방지 없음 → `session/prompt`가 session_id 없이 실행됨

**수정 방향 — `SessionWorkspace.on_mount()` 흐름 변경:**
```python
async def on_mount(self):
    # 1. 입력 비활성화 + 연결 중 표시
    self.input_area.can_focus = False
    self.add_system_message("🔄 ACP 연결 중...")
    
    try:
        self.acp_client = ACPClient(...)
        await self.acp_client.start()
        # 이제 send_request가 응답을 기다리므로 순차적으로 진행
        await self.acp_client.initialize()
        resp = await self.acp_client.create_session(cwd=".")
        # session_id 추출
        session_id = resp["result"]["sessionId"]
        self.acp_client.set_session_id(session_id)
```

## 🔍 [리뷰어] 근본 원인 발견: `call_from_thread` → `call_next` 교체 필요 (2026-07-23)

### 현상
- `test_acp/test_acp.py` 직접 통신 테스트: ✅ 정상 (print로 즉시 출력)
- 실제 Nexus UI(앱): ❌ 응답 출력 안됨
- hermes sessions 확인 시 프롬프트 전송 및 응답 확인 가능

### 근본 원인

`acp.py:106-107`의 `_handle_notification`:
```python
if self.app and hasattr(self.app, "call_from_thread"):
    self.app.call_from_thread(self.on_message, data)
```

**`_listen_loop`는 별도 thread가 아님** — `asyncio.create_task()`로 생성된 asyncio task이므로, **동일한 이벤트 루프**에서 실행됨.

Textual의 `call_from_thread`는 **다른 OS thread**에서 호출할 때 `self.post_message_threadsafe()`를 통해 메인 이벤트 루프 메시지 큐에 넣는다. 그러나 **동일한 asyncio task**에서 호출하면 이벤트 루프가 이미 실행 중이므로 메시지 큐에 넣지 못하고 **silently fail**함.

→ notification이 수신됨 → `call_from_thread`가 실패 → 콜백(`_handle_acp_message`)이 호출 안됨 → UI에 반영 안됨.

### 해결책

`call_from_thread` → `call_next`로 교체:
```python
# acp.py:102-113
async def _handle_notification(self, data: Dict[str, Any]):
    if self.app and hasattr(self.app, "call_next"):
        self.app.call_next(self.on_message, data)
    else:
        if asyncio.iscoroutinefunction(self.on_message):
            await self.on_message(data)
        else:
            self.on_message(data)
```

**동일하게 `_handle_response`도 수정 필요** (line 124-130) — response도 notification과 동일하게 UI로 라우팅됨.

### 에이전트별 유연한 파싱 전략

hermes acp는 `params["update"]` 중첩 구조, opencode는 `params`顶层 구조를 쓸 수 있으므로:
```python
# session_workspace.py:124-129
if method == "session/update":
    # 중첩 구조가 있으면 그걸 사용하고, 없으면 params顶层 직접 사용
    update = params.get("update") or params
    update_type = update.get("sessionUpdate")
    content = update.get("content", {})
```

→ `update = params.get("update")`가 `None`이면 `or params`로 폴백. 중첩 여부와 무관하게 동작.

### 수정 파일
1. `src/core/acp.py` — `call_from_thread` → `call_next` 교체 (`_handle_notification`, `_handle_response`)
2. `src/widgets/session_workspace.py` — `update = params.get("update") or params`로 유연한 파싱 적용
